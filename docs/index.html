01Artistic vision

Artistic Vision

Our group had three people, so we started by brainstorming games all three of us could play together—and that would work with the ESP32’s small screen and two buttons.

UNO was the first game we thought of. We all knew it, enjoyed playing it, and liked the interaction it creates between players. We also considered Mario Kart, Wii Sports, Overcooked, and Among Us.

UNO / SelectedMario KartWii SportsOvercookedAmong Us

We voted for UNO because its turn-based rules seemed more manageable to implement on the ESP32. Instead of real-time movement or complex controls, each player could use two buttons to browse cards and make a move.

We drew our first interface on an iPad, then developed the screen layouts in Figma. The goal was to keep the recognizable parts of UNO—colors, cards, and changing turns—while making them readable on a handheld display.

Game Rules and Adaptation

Each player sees their own hand and the shared discard pile. Players match a card by color, number, or action, while Wild cards let them choose the next color. Skip, Reverse, +2, and +4 change the flow of play. The first player to empty their hand wins.

Our implementation generates cards randomly using the classic 108-card categories: 76 number cards, eight each of Skip, Reverse, and Draw Two, and four each of Wild and Wild Draw Four. It does not maintain a finite physical deck.

Read the UNO rules ↗

This is a digital adaptation. The current version does not implement a manual “UNO” call-out penalty or the full scoring system.

02My contribution

My Contribution

I built on Ishani and Yunte’s sketches and Figma designs by playing through the interface, giving feedback, and refining it from a player’s perspective.

My role focused on informal playtesting and UI improvements. Two things kept interrupting the experience: not knowing how many cards everyone had left, and not being sure whose turn it was.

01 / Card counts

Player Card Counts

The original interface did not show everyone’s remaining cards. In UNO, that information matters: the goal is to empty your hand, and +2, +4, and drawing can change the counts quickly.

I proposed a persistent row at the bottom, with “You” in the middle and the other two players on either side. It lets players check the state of the game without losing their place in their hand.

02 / Turn indicators

Screen Brightness and Turn Indicators

Reverse and Skip cards, along with communication delays, made it hard to tell who should play next.

I proposed keeping the active player’s screen bright and dimming the others. The current player’s label also turns yellow, while the other labels remain white. Together, these cues make the turn visible at a glance.

03Technical implementation

Technical Implementation

Making turns easier to see

While playing, I kept losing track of whose turn it was, especially after a Skip or Reverse. I suggested dimming the screen when it wasn’t your turn. The code checks the current player before showing the screen:

drawPlayingScreen();
if (game.turn != PLAYER_ID) {
  dimSprite();
}

dimSprite() dims the drawn image to 45% brightness. I also proposed showing everyone’s card counts at the bottom, with “You” in the middle and the current player’s label in yellow. Both cues use game.turn, so they follow the turn even when an action card changes the order.

Getting the same code to work for all three of us

Whenever one of us changed the code, we pushed it to GitHub so the other two could copy it into Arduino IDE. Often it would compile on one person’s computer but give errors on the others. We had to keep going back and fixing things. Pasting the errors into AI made debugging much easier.

One line we fixed several times was onReceive. My ESP32 package was version 3.3.12, which needed a different first parameter:

// Old
const uint8_t *mac

// Updated for ESP32 3.3.12
const esp_now_recv_info_t *info

The receive logic stayed the same. But the old line kept coming back when we copied another version, so we had to check that Arduino was actually opening the updated file before compiling.

Wild cards

We also had trouble telling which color had been selected after a Wild or +4. The updated interface shows the color name while choosing, saves it in game.topColor, and uses that color on the discard pile after confirmation.

05AI support

AI Support

Our code grew out of the Lab 3 starter provided by Professor Tseng. We also used AI to help develop and debug the implementation. We made the design choices ourselves, then brought specific code problems and interaction issues to the tools.
